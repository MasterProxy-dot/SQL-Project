# FinTech Risk Analytics: Credit Card Fraud Architecture & Pipeline

## Executive Summary
This project designs and implements an end-to-end relational database architecture in PostgreSQL to ingest, stage, and profile a massive financial dataset containing **284,807 transactions**. By applying advanced SQL aggregations and time-series logic, this pipeline exposes distinct behavioral anomalies and systemic risk patterns, isolating automated off-hours velocity attacks and calculating high-variance fraud signatures to protect corporate capital.

## Core Financial & Behavioral Findings
* **The Macro Exposure:** While fraudulent transactions represent only **0.1727%** of total credit card volume, they account for **$60,127.97** in straight-line losses. 
* **Ticket Size Anomaly:** Fraudulent behavior deviates significantly from normal spending habits. The average legitimate transaction size sits at **$88.29**, whereas the average fraudulent ticket size climbs to **$122.21**, proving that perpetrators actively maximize transaction values while intentionally capping charges below a maximum threshold of **$2,125.87** to evade standard large-purchase banking alarms.
* **The Off-Hours Vector:** Time-series analysis via cyclic modulo routing reveals that the system baseline fraud rate surges from its 0.17% average to a staggering **1.7127% at 2:00 AM**—a **10x spike**—confirming automated script-testing routines execution while users are fast asleep.
* **Triangulating the Tripwires:** Statistical profiling on anonymized PCA features reveals extreme structural anomalies. For example, feature `V14` drops violently from an expected normal baseline of **+0.0121** down to a compromised signature of **-6.9717** during fraud events.

## Technical Challenges Solved

### 1. Inbound Scientific Notation Normalization
* **Problem:** Source data strings generated by spreadsheet formatting engines caused system parsing errors (`invalid input syntax for type integer: "1e+05"`) when writing raw indicators directly to standard integer columns.
* **Solution:** Re-engineered the database staging architecture by isolating inputs into highly scalable `NUMERIC` and floating-point columns, allowing PostgreSQL to natively translate scientific strings into true numbers.

### 2. Time-Series Granularity Decomposition
* **Problem:** The system transactional clock was encoded as linear elapsed seconds rather than human-readable timestamps, blocking structural `GROUP BY` categorical buckets.
* **Solution:** Implemented structural cyclic modular math (`FLOOR((transaction_time % 86400) / 3600)`) to cleanly collapse active tracking data into 24 static hourly blocks.
